# Retro Visualizer - embed build (Android TV launcher)

Target: MXQ Pro class box - Android 7.1.2, system WebView = Chrome 76, Mali-450 (GLES2), 1 GB RAM, 32-bit,
UI 1280x720. Files: `index.html` + `visualizer.js` (generated by `node dist/tools/build-embed.js`; readable
sources in `src/` and `../web/`). No Music panel, no network, no CSS/JS newer than Chrome 76 (checked by
`dist/test/embed.test.js` with an ES2019 parser).

## JS API (on `window`, also `window.RetroVisualizer`)

| call | |
|---|---|
| `feedPcm(Int16Array L, Int16Array R or null, sampleRate)` | PCM -> exact analysis (30 frames/s, 2048-sample window) |
| `feedPcmBase64(base64, channels, sampleRate)` | interleaved little-endian int16, the cheap path from Kotlin |
| `feedLevel({freq, wave})` | ready-made bytes: `[L, R]` or one array (mono), 1024 each |
| `setVisualizer('battery' or 'barswaves')` | plasma / spectrum (remembered) |
| `listPresets()`, `setPreset(nameOrIndex)`, `currentPreset()` | plasma lists `Random` first |
| `setOriginals(bool)`, `loadClassicPack(urlOrObject)` -> Promise | classic pack exported from the desktop player |
| `setSize(w, h)` (max 1280x720), `pause()`, `resume()` | |
| `setIdle('silence' or 'demo')`, `getStats()` | idle = nothing fed for 2 s |

Buffers: plasma draws at 288 rows x window aspect (512x288 at 16:9) and is scaled up (pixelated); spectrum
draws at half size above 960 px wide (640x360 for 720p). Engines run 30 steps/s whatever the display rate.
After warm-up the feed path allocates nothing; the render path allocates almost nothing (see numbers).

Classic presets on the box: on a Windows PC open `web/index.html`, *Classic* > pick wmp.dll > *Export classic
pack*, copy `classic-pack.json` to e.g. `/sdcard/RetroLauncher/Visualizer/classic/classic-pack.json`, then
`loadClassicPack('file:///sdcard/RetroLauncher/Visualizer/classic/classic-pack.json')` once (it is stored in
the WebView's localStorage). Needs `allowFileAccess` and, for file:// pages, `allowFileAccessFromFileURLs`
(or pass the parsed JSON object / string instead of a URL).

## Kotlin side (sketch)

```kotlin
val web = WebView(ctx).apply {
    settings.javaScriptEnabled = true
    settings.domStorageEnabled = true                    // localStorage: classic pack, last visualizer
    settings.allowFileAccess = true
    @Suppress("DEPRECATION") settings.allowFileAccessFromFileURLs = true   // XHR of the classic pack
    setLayerType(View.LAYER_TYPE_HARDWARE, null)
    setBackgroundColor(Color.BLACK)
    loadUrl("file:///android_asset/visualizer/index.html")   // or a copy on /sdcard
}

// PCM tap: e.g. your own player's AudioTrack data, or android.media.audiofx.Visualizer (waveform only, 8-bit:
// then build feedLevel() arrays instead). Push ~4-8 chunks per second, not one per audio buffer:
// each evaluateJavascript costs a thread hop + a string copy, so batch.
private val pending = ByteArrayOutputStream()
fun onPcm(interleaved16: ShortArray, frames: Int, rate: Int) {           // audio thread
    val bb = ByteBuffer.allocate(frames * 4).order(ByteOrder.LITTLE_ENDIAN)
    bb.asShortBuffer().put(interleaved16, 0, frames * 2)
    synchronized(pending) { pending.write(bb.array()) }
    if (pending.size() >= rate / 6 * 4) flush(rate)                       // ~166 ms of stereo audio
}
private fun flush(rate: Int) {
    val b64 = synchronized(pending) { Base64.encodeToString(pending.toByteArray(), Base64.NO_WRAP).also { pending.reset() } }
    web.post { web.evaluateJavascript("feedPcmBase64('$b64',2,$rate)", null) }   // UI thread
}

// launcher events
web.evaluateJavascript("setVisualizer('barswaves');setPreset('Aurora')", null)
web.evaluateJavascript("listPresets()") { json -> /* ["Random","Candy Ripple",...] */ }
override fun onPause() { web.evaluateJavascript("pause()", null); web.onPause() }
override fun onResume() { web.onResume(); web.evaluateJavascript("resume()", null) }
```

Alternative: `addJavascriptInterface(obj, "Host")` with a `@JavascriptInterface fun pull(): String` that JS
polls each step returns the latest base64 chunk - avoids evaluateJavascript string building on the UI thread,
but adds a binder hop per call from the JS thread. For 44.1 kHz stereo, base64 is ~235 KB/s; both ways are
fine at 6 calls/s. Lower the cost further by sending mono (channels = 1) or 22.05 kHz (the analysis re-bins to
0..22 kHz either way; wave bytes then differ slightly from 44.1 kHz).

## Measured frame cost

Chrome (desktop, this PC) via the Browser pane, 1280x720 output, per engine step incl. putImageData + drawImage
submit (GPU work is asynchronous). "x6" = DevTools "6x CPU slowdown" convention (a Cortex-A53 box running
Chrome 76 can be slower still - measure on the device with `getStats()`):

| scene | ms/frame | x6 | |
|---|---|---|---|
| plasma Random, 512x288 | 2.84 | 17.1 | max 11 ms |
| plasma own preset (Ember Bloom) | 2.39 | 14.4 | |
| plasma own preset (Prism Drift) | 1.09 | 6.5 | |
| spectrum Aurora, 640x360 | 1.34 | 8.0 | |
| spectrum Neon Rain, 640x360 | 1.18 | 7.1 | |
| feedPcm, 1024 stereo samples (node) | ~0.5 | ~3 | 0 GC |

Budget at 30 steps/s is 33 ms, so with 6x the scenes fit; the heaviest classic presets (JDar line drawers)
measured ~6-9 ms in node (x6: 36-55 ms) and would drop to ~20 fps on a 6x-slower CPU.
Total size of dist/embed: see the top-level report (about 150 KB, uncompressed).
